# Deploying DisputeShield to Render

The blueprint (`render.yaml`) creates two services: `disputeshield-api` (Python, **starter plan + 1 GB disk**
for SQLite, one worker) and `disputeshield-web` (static site). Decision: SQLite on the persistent disk for the
hackathon (PROGRESS G12); the free plan has no disk and sleeps, which would wipe data.

## 1. Create the services
1. Push this repo to GitHub (it's a local git repo today; nothing has been pushed).
2. Render dashboard → **New → Blueprint** → pick the repo. Render reads `render.yaml`.
3. Fill the secret values it asks for (`sync: false`):

| Key | Value |
|---|---|
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | from your sandbox app |
| `PAYPAL_WEBHOOK_ID` | after step 3 below (leave empty first) |
| `GROQ_API_KEY`, `GEMINI_API_KEY` | your LLM keys (Gemini also does the troubleshooting web research: Grounding with Google Search, 5,000 free searches/month on Gemini 3+) |
| `TAVILY_API_KEY` | optional research fallback (tavily.com, 1,000 free credits/month) |
| `STORE_NAME` (optional) | shown in the buyer help page header (default "Demo store") |
| `PROOF_VISION_CHECK` (optional) | `true` turns on the advisory Gemini look at buyer proof photos. Leave `false` on a free Gemini key (free-tier inputs may be human-reviewed; photos can be personal). See PROGRESS G50. |
| `ADMIN_TOKEN` | any long random string (sandbox demo helpers) |
| `MERCHANT_LOGIN_EMAILS` | the PayPal email allowed to log in (your sandbox **business** account) |
| `AUTH_REDIRECT_URI` | `https://disputeshield-api.onrender.com/api/auth/paypal/callback` (your API host) |
| `FRONTEND_URL` | `https://disputeshield-web.onrender.com` (your static site host) |
| `CORS_ORIGINS` | same as `FRONTEND_URL` |
| `VITE_API_BASE_URL` (static site) | `https://disputeshield-api.onrender.com` |

`AUTH_SECRET` is generated by Render.

Buyer proof files live under `ARTIFACTS_DIR/ts/` on the API host's disk (use a persistent disk on Render, or
they're lost on redeploy). Videos over 10 MB get an evidence-size copy only if `ffmpeg` is on the host
(PROGRESS G51); everything else works without it.

## 2. PayPal app settings (developer.paypal.com → Apps & Credentials → Sandbox → your app)
- **Log in with PayPal**: enable it → *Advanced settings* → Return URL = your `AUTH_REDIRECT_URI`
  (keep `http://localhost:8000/api/auth/paypal/callback` too for local development) → tick **Email** →
  privacy policy / user agreement URLs (`https://example.com` is fine in sandbox) → Save.

## 3. Webhook
```bash
cd backend && python -m app.scripts.register_webhook --url https://disputeshield-api.onrender.com/webhooks/paypal
```
It re-points the existing webhook (or creates one). Put the printed id in Render's `PAYPAL_WEBHOOK_ID`.

## 4. Check
- `https://<api-host>/health` → `{"status":"ok"}`
- Open the static site → **Log in with PayPal** with the allowed account → the queue loads.
- Live updates (SSE) through Render's proxy: open a case and watch the timeline status say **Live**
  (PROGRESS G11: not yet verified on Render).

## 5. Privacy: buyer signals and retention (Phase 15)

DisputeShield compares a disputed order with the buyer's earlier orders: same device, network, shipping address
or PayPal account. This gives evidence similar to Visa Compelling Evidence 3.0 for unauthorised-payment claims.
It is not Visa CE 3.0 itself, and PayPal disputes don't follow it.

- **What is stored:** at checkout the server keeps only keyed hashes (HMAC-SHA256, truncated to 128 bits) of:
  - the client IP (the first `X-Forwarded-For` hop on Render)
  - a device fingerprint: the browser hashes user agent + screen size/colour depth + time zone before sending,
    and the server hashes it again
  - the PayPal payer id
  Raw IPs, fingerprints and payer ids are never written to the database or logs. Shipping addresses are kept on
  the order anyway (needed to ship); they are compared through the same normalised hash.
- **Key:** set `SIGNAL_HASH_KEY` (a long random string, kept secret like `AUTH_SECRET`). Unset, it falls back to
  `AUTH_SECRET`, then to a development key. Changing it makes old and new hashes incomparable (no matches across
  the change), and nothing else.
- **What the merchant sees:** which kinds of identifiers matched ("matched on device + address", "CE 3.0-like
  match"), never the values or hashes.
- **Retention:** the hashes are cleared from orders `SIGNAL_RETENTION_DAYS` after the order (default 400: the
  365-day comparison window plus margin), by the app's 6-hourly retention job or `python -m app.scripts.purge_proofs`.
  Buyer proof files and merchant uploads follow `PROOF_RETENTION_DAYS` after the dispute is resolved.
- **Serial disputes:** counted from the store's own dispute records (same buyer email or payer id, 12 months).
  This is shown to the merchant as context only; it never decides a case, and the wording sent to PayPal is
  neutral.

## 6. Alerts and MCP (Phase 17)

- **Alerts:** set `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` for email (STARTTLS) and/or
  `SLACK_WEBHOOK_URL` for Slack. The merchant picks the address and the alert kinds in Settings. Each alert is sent
  once (processed_events key) by a 60-second background loop (`ALERTS_INTERVAL_S`).
- **MCP:** set `PUBLIC_API_URL` to the backend's public https URL. The MCP endpoint is `<PUBLIC_API_URL>/mcp`. The
  merchant creates the bearer token in Settings (only its hash is stored). See README, "Use DisputeShield from
  Claude Desktop".
